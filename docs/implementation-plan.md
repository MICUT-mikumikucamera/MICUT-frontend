# MiCut 디자인 시스템 적용 및 통합 계획

기준일: 2026-11-06. 대상: `feat/scaffold-brand` (`ad6bf56`, origin과 동기화). 비교 기준: `feat/initial-design` (`3223171`). 새 디자인 규칙은 `docs/design-system.md`의 사용자 제공 내용을 따른다. 예전 무드보드 해석과 충돌하면 사용자 제공 규칙이 우선한다.

## 1. 이번 변경: 확인된 수치부터 공통 구현에 적용

| 담당 | 소유 범위 | 산출물 |
| --- | --- | --- |
| 디자인 토큰 에이전트 | core/theme의 colors, spacing, typography 및 토큰 테스트 | 제공된 Gray 값과 bg/text/icon/border Semantic, 20px 화면 여백, spacing/radius 스케일, 역할별 Pretendard 스타일 |
| 컴포넌트 에이전트 | core/widgets 및 gallery_screen | CTA 간격 8px, 내비게이션 아이콘·레이블 4px, 갤러리 하단 영역 상단·좌우 20px/하단 32px, 해당 모달의 20px 여백·16px 간격 |
| 통합 계획 에이전트 | 이 문서만 | 기존 기능 차이, 후속 통합 순서와 검증 기준 |
| 주 에이전트 | 통합·검증·문서 정합성 | 공용 API 호환성, 테스트 결과, 변경 범위 보고 |

- 기존 테마 호출 이름은 호환 별칭으로 유지하고 화면별 복사 값을 추가하지 않는다. Semantic 역할은 같은 색이어도 각각 유지한다.
- Typography의 자간은 fontSize × -0.02이며 Heading/Label/Detail은 1.4배, Body 24/20은 1.4배, Body 18/16/14는 1.5배다.
- 토큰 변경이 모든 화면에 미치는 영향은 통합 담당자가 확인한다. 화면 구조, API, 라우팅, 저장소는 이 단계에서 개편하지 않는다.
- Pretendard 400/500/600/700은 현재 등록된 로컬 에셋을 사용한다. DungGeunMo는 제공되지 않았으므로 대체 폰트로 완성 처리하지 않는다.
- 기존 브랜드 색상·그라데이션·HUD 등은 미확정 레거시로 표시한다. 보존하는 것은 새 디자인 승인이나 시안 일치의 의미가 아니다.

## 2. Figma 확인 후 전체 화면 적용

아직 필요한 자료: Primary/Secondary/Red/Green 실제 색상과 Semantic 매핑, gra/bg·gra/radial 방향과 스톱, CTA1/CTA2 등의 변형·크기·반경·상태, 아이콘·정적 이미지, 화면별 배치. 미제공 값은 Tailwind 기본값이나 기존 무드보드로 확정하지 않는다.

자료가 확보되면 통합 담당자가 노드→화면→공통 컴포넌트 매핑을 확정하고 공통 컴포넌트를 먼저 완성한다. 이후 충돌하지 않도록 아래 화면 폴더를 나눈다.

- 촬영 담당: 촬영 가이드·카메라·확인·처리·실패·결과. 실제 카메라 제어와 이미지 처리 계약은 보존한다.
- 탐색 담당: 홈·갤러리·사진 상세·컬렉션·카드 상세·설정. 디자인에 없는 새 배지·장식·기능을 추가하지 않는다.
- 통합 담당: 공통 테마/컴포넌트, 앱 라우터, assets/pubspec, 화면별 리뷰 및 시각 검증. 화면 담당은 이 파일들을 병렬 수정하지 않는다.

디자인 시스템에 정의된 컬렉션 획득 연출이나 위험 행동의 스타일은 해당 서버 기능이 지원된다는 근거가 아니다. 획득·성공·삭제 결과를 임의 생성하지 않는다.

## 3. 기존 실제 기능의 통합: 별도 후속 작업

이번 브랜치 전환은 기존 기능의 병합이 아니다. 이전 구현은 `feat/initial-design`에 그대로 남아 있다. 아래 차이를 해결하기 전 실제 서비스 연결/기능 동등성을 선언하지 않는다.

| 항목 | scaffold-brand에서 확인한 차이 | 통합 기준 |
| --- | --- | --- |
| 실행 설정 | 기본은 랜덤 FakeJobRepository; MICUT_REAL_API/MICUT_API_URL | API_BASE_URL을 실제 연결의 표준 입력으로 복원하고 기존 MICUT 설정은 호환 입력으로 유지. 명시적 주소가 충돌하면 구성 오류로 처리 |
| 업로드 | multipart의 capture JSON 필드 사용 | 기존 계약대로 photo JPEG + w/h/rotation 필드, fx 생략. 계약 fixture와 요청 테스트로 검증 |
| 사진 처리 | 파일 원본 전달 및 rotation=0; 정규화/크롭 보장 없음 | EXIF 회전·반전 정규화 후 실제 전송 JPEG 기준 치수, 카메라 중앙 3:4 프리뷰·확인·전송 일치, 앨범 원비율 |
| 작업 수명 | 화면 소유 스트림, 2초 직렬 폴링; 지속 작업 저장·복원 없음 | Riverpod 상태 소유자로 옮겨 응답 후 1.5초 직렬 조회, 백그라운드 중단, 저장한 job 복구 및 수동 재조회 |
| 처리 중 취소 | active job에 discard 요청 | 화면만 닫고 서버 작업은 유지. 실패 작업 discard만 성공 후 이탈; 실패 시 작업과 재시도 경로 유지 |
| 결과 URL | http로 시작하면 그대로 허용 | 기존 구현처럼 설정된 서버 origin 내 결과만 허용하고 상대 URL을 안전하게 해석 |
| 저장 | 파일 기반 gallery.json, 환경 구분 없음 | 실제 서버별·Fake별 데이터 격리. 기존 SharedPreferences URL 기록은 삭제하지 않고 읽기 호환 경로로 유지; 다운로드 실패를 빈 파일/성공으로 대체하지 않음 |
| 오류 복구 | 일부 discard/get 실패가 처리되지 않음 | 재시도 조건·중복 요청 방지·지속 오류 표시 및 오류 후 동일 작업 유지 |
| 플랫폼 | tracked Android 중심; web/iOS 프로젝트 없음, dart:io 사용 | 플랫폼 복구를 별도 변경으로 수행. 작업 트리의 untracked ios가 완전한 프로젝트라고 가정하지 않음 |
| 테스트 | 기본 버튼/카드 위젯 2개 | 기존 촬영비율·API·복구 시나리오를 새 구조에 맞춰 이전하고 유지 |

수행 순서: 계약 fixture/회귀 테스트 복원 → Repository 업로드·URL 수정 → 촬영 정규화 → Riverpod 작업 상태·복구 → 저장 호환·플랫폼 검증. 기존 ChangeNotifier 전체를 병합하는 대신 새 Riverpod/go_router 구조에 필요한 동작을 이식한다. 실제 백엔드 주소·업로드 한도 등 미확정 서버 운영값을 만들어내지 않는다.

## 4. 검증 및 완료 기준

이번 단계:

- 변경 Dart 파일 format 검사, `flutter analyze`, `flutter test` 실행.
- 토큰 테스트로 Semantic 값/별도 역할, 20px 기본 간격, 등록 반경, TextStyle의 실제 줄 간격·자간을 확인.
- 기존 버튼 탭/카드 테스트를 유지하고 변경된 공통 위젯과 갤러리 하단 영역을 좁은 화면에서도 확인. 글자 확대·SafeArea에서 버튼이 가려지거나 overflow가 없어야 한다.
- 실제 렌더링 가능한 환경에서 320×640, 390×844 화면을 검토. Figma 미확인 상태에서는 스크린샷 일치 완료로 보고하지 않는다.

기능 통합 단계: 촬영/앨범 → 명시적 업로드 → 성공/실패/재시도/폐기, 네트워크 중단·백그라운드·재시작 복구, 갤러리 저장·선택 삭제·실패 보존, 권한 거절을 검증한다. 업로드 재시도는 자동 수행하지 않는다.

환경 한계: 현재 WSL PATH의 flutter는 Windows SDK 경로다. UNC 파일 잠금 오류가 나면 Linux SDK 또는 Windows 로컬 검증 사본을 사용한다. 웹 검증은 web 플랫폼 복원 이후, iOS 빌드/권한은 macOS/Xcode에서, 카메라·사진첩·공유는 실제 기기에서 확인한다. 실행하지 못한 항목은 통과로 기록하지 않는다.
