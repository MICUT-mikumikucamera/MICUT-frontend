# 백엔드 전달: 원본 사진 및 크롭 좌표 수신 변경

작성일: 2026-11-08

## 변경 목적과 적용 상태

프런트에서 크롭된 사진 대신 **전체 원본 사진과 크롭 영역을 함께 전송**하도록 변경했습니다. 전체 이미지로 depth를 분석하고, 지정한 영역을 최종 결과로 출력하기 위한 변경입니다.

현재 프런트 전송 구현과 자동 테스트는 완료됐습니다. 아래 내용은 백엔드에 적용해야 할 계약이며, 실제 서버의 수신·처리 변경과 연동 검증은 아직 완료되지 않았습니다.

## 1. 요청 형식

`POST /api/v1/jobs` · `multipart/form-data`

| 필드 | 형식 | 필수 | 설명 |
| --- | --- | --- | --- |
| `photo` | 파일 | O | 크롭·축소하지 않은 전체 화각 JPEG |
| `w` | 정수 문자열 | O | 전송 이미지의 실제 가로 픽셀 |
| `h` | 정수 문자열 | O | 전송 이미지의 실제 세로 픽셀 |
| `rotation` | 정수 문자열 | O | 현재 항상 `0` — 방향 정규화 완료 |
| `fx` | 실수 문자열 | X | 알 수 있을 때만 전송. 현재 프런트에서는 생략 |
| `crop` | JSON 문자열 | O | 최종 출력에 사용할 사각형 |

`crop`은 JSON 요청 본문이나 별도 파일이 아니라 **multipart의 텍스트 필드**입니다. 폼 필드에서 읽은 뒤 JSON 객체로 파싱해 주세요.

### 요청 예시

4000×3000 이미지의 중앙을 세로 3:4로 사용한다면 다음과 같습니다.

```text
photo: micut-original.jpg (파일)
w: "4000"
h: "3000"
rotation: "0"
crop: {"x":875,"y":0,"width":2250,"height":3000}
```

위 예시의 `crop` 필드 값 자체는 아래 JSON 텍스트입니다. 백슬래시를 추가하거나 JSON 문자열로 이중 인코딩하지 않습니다.

```json
{"x":875,"y":0,"width":2250,"height":3000}
```

## 2. 원본과 좌표 기준

- 프런트에서 EXIF 회전·반사를 이미지 픽셀에 적용한 후 전송합니다. 서버에서 추가로 회전하지 않아야 합니다.
- `w`, `h`는 방향 정규화가 끝난 **실제 전송 이미지**의 크기입니다. 촬영 파일의 회전 적용 전 크기가 아닙니다.
- `crop`은 전송 이미지의 좌상단을 `(0, 0)`으로 하는 **정수 픽셀 좌표**입니다. 비율 좌표나 화면 좌표가 아닙니다.
- `x`, `y`는 크롭 시작 위치이고, `width`, `height`는 크롭 영역의 폭과 높이입니다.
- 사용할 영역은 `[x, x + width)`, `[y, y + height)`입니다. 우측·하단 끝 좌표는 포함하지 않습니다.
- 위 예시를 이미지 배열로 자르면 `image[0:3000, 875:3125]`입니다.
- “원본”은 전체 화각·해상도 보존을 의미합니다. 방향 정규화와 JPEG 재인코딩을 하므로 촬영 파일의 바이트와 완전히 같지는 않습니다.
- 카메라 촬영은 선택한 비율의 중앙 크롭 영역을 전달합니다. 앨범 사진은 기본적으로 사진 전체를 크롭 영역으로 전달합니다.

프런트에서는 원본과 표시용 크롭 이미지를 분리해 보관합니다. 사용자는 최종 크롭 영역 전체를 확인하지만, 서버에는 더 넓은 원본을 전송합니다.

## 3. 서버 수신 검증

1. `photo`를 이미지로 디코딩하고 `w`, `h`, `rotation`을 정수로 파싱합니다.
2. `crop` 텍스트를 JSON 객체로 파싱하고 네 필드가 정수인지 확인합니다.
3. 이미지의 실제 크기가 `w`, `h`와 일치하는지 확인합니다.
4. 다음 조건을 모두 검증합니다.

```text
w > 0
h > 0
rotation == 0
x >= 0
y >= 0
width > 0
height > 0
x + width <= w
y + height <= h
```

잘못된 영역을 자동 보정하거나 `crop`을 조용히 무시하지 말고 요청 오류로 처리해 주세요. 구체적인 오류 코드와 HTTP 상태 코드는 백엔드 계약에 맞춰 확정해야 합니다.

기존 파일 형식·용량 제한은 유지합니다. 전체 원본을 보내므로 기존 크롭 파일보다 전송 용량이 커질 수 있습니다.

## 4. 분석·합성·출력 순서

1. **크롭하기 전 전체 이미지로 depth·장면 분석**을 수행합니다.
2. 원본 좌표계에서 크롭 영역을 고려해 합성합니다. 최종 영역 밖으로 주요 피사체가 배치되지 않도록 크롭 정보를 활용합니다.
3. 마지막에 해당 영역을 잘라 결과 이미지를 생성합니다.
4. 기존 결과 응답의 `result.image_url`로 최종 이미지를 제공합니다.

분석 과정에서 이미지를 축소한다면, 크롭 좌표도 해당 축척에 맞춰 변환해야 합니다. 가로·세로 축척이 다르다면 각각 적용합니다. 원본 좌표와 분석용 이미지 좌표를 혼용하지 않아야 합니다.

재시도 시에는 최초 원본과 크롭 좌표를 그대로 재사용해 주세요. 원본 삭제·보관 정책과 retry/discard 흐름은 기존 v0 계약을 유지합니다.

## 5. 기존 계약과 달라지는 부분

- 기존 프런트 코드의 `capture` JSON 묶음 전송을 없애고, v0 명세대로 `w`, `h`, `rotation`, `fx`를 개별 폼 필드로 보냅니다.
- 새 `crop` 폼 필드를 추가합니다.
- `photo`는 최종 비율로 잘린 이미지가 아니라 전체 화각 이미지입니다.
- 응답에는 기존 `capture` 객체 안에 `crop`을 함께 보존해 주세요. 생성 및 상태 조회 응답 모두 같은 정보를 유지해야 합니다.

### 응답의 capture 부분 예시

```json
{
  "capture": {
    "w": 4000,
    "h": 3000,
    "rotation": 0,
    "fx": null,
    "crop": {
      "x": 875,
      "y": 0,
      "width": 2250,
      "height": 3000
    }
  }
}
```

프런트는 `crop`이 없는 과거 job 응답도 읽을 수 있습니다. 다만 신규 요청의 `crop`을 구서버가 무시하는 경우까지 호환된다는 의미는 아닙니다. 프런트에는 실패 시 크롭 이미지를 대신 보내는 자동 우회 동작이 없습니다.

## 6. 백엔드 적용 확인 항목

- [ ] multipart의 개별 필드와 `crop` JSON 문자열을 수신한다.
- [ ] 이미지 크기와 크롭 범위를 검증한다.
- [ ] 전체 이미지로 depth를 분석하고 좌표계를 일관되게 사용한다.
- [ ] 최종 결과에 요청한 크롭 영역을 적용한다.
- [ ] 생성·조회 응답의 `capture.crop`을 보존한다.
- [ ] retry 시 동일한 원본과 크롭 정보를 재사용한다.
- [ ] 프런트와 실제 서버를 연결해 세로·가로·정사각형 사진 및 EXIF 방향이 있는 사진을 확인한다.
